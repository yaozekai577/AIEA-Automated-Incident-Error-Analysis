## 1. 项目背景与目标

### 1.1 背景

线上与本地开发环境的异常往往依赖人工排查：翻日志、群里同步、手填 Jira。流程长、重复劳动多，且同类错误反复出现时缺少沉淀。本工具旨在把「发现错误 → 理解原因 → 通知协作方 → 建单跟进」自动化，缩短平均故障响应时间（MTTR）。

### 1.2 核心目标（一周内必须达成）

| 目标 | 说明 |
|------|------|
| 错误捕获 | 支持线上服务与本地开发环境的异常/日志上报 |
| 智能分析 | 调用大模型对错误做根因分析并给出修复建议 |
| 协作推送 | 将分析结论推送到飞书 **或** 钉钉群聊（二选一优先打通，另一端预留适配） |
| 工单闭环 | 自动创建 Jira 工单，并在推送消息中附带工单链接 |
| 可演示 | 端到端 Demo + 基础管理配置 + 简要使用说明 |

### 1.3 成功定义

用一条人为构造的异常（本地 SDK/Agent 上报），在 60 秒内完成：入库 → LLM 分析 → 群消息推送 → Jira 工单创建，且同一指纹错误在冷却窗口内不重复建单/刷屏。

## 2. 范围界定（MVP）

### 2.1 纳入范围（In Scope）

- Java Agent / SDK 轻量上报（异常堆栈、环境、服务名、版本、请求 ID 等）
- 服务端接收、去重、异步分析流水线
- 大模型 Prompt 编排（根因 + 修复建议 + 置信度）
- 飞书机器人 **或** 钉钉机器人消息推送（MVP 主推其一）
- Jira Cloud/Server REST API 创建 Issue
- 简单 Web 配置页（Webhook、LLM Key、Jira 项目、去重策略）
- 错误指纹与抑制策略（防刷屏）
- 基础审计日志与处理状态查询 API

### 2.2 明确不做（Out of Scope，留到二期）

- 多租户计费、复杂权限体系
- 自动提交 PR / 自动改代码
- 全量 APM（分布式链路完整替代 SkyWalking/Pinpoint）
- 多 LLM 供应商热切换与评测平台
- 知识库 RAG 深度调优（仅预留接口与简单相似错误检索）
- 飞书 + 钉钉双通道同时深度打磨（主通道完成即可）

### 2.3 假设前提（需在 Day0/Day1 确认）

1. 公司已有可用的大模型 API（OpenAI 兼容或通义/文心/DeepSeek 等），且具备内网可达或代理方案  
2. 飞书/钉钉机器人 Webhook 或开放平台应用权限可申请到位  
3. Jira 具备 API Token / 服务账号，且有创建 Issue 的权限  
4. 目标业务应用为 Java（Spring Boot 优先），可引入轻量 SDK 依赖  
5. 可在内网部署一台开发/演示用服务器（或本机 Docker）

## 3. 技术栈选型

### 3.1 推荐技术组件一览

| 层级 | 推荐选型 | 备选 | 选型理由 |
|------|----------|------|----------|
| 语言 | **Java 17** | Java 21 | LTS，企业环境兼容性好；与 Spring Boot 3.x 匹配 |
| 框架 | **Spring Boot 3.3+** | Micronaut / Quarkus | 生态成熟、集成快、一周交付风险最低 |
| 构建 | **Maven** | Gradle | 公司内常见、依赖管理直观 |
| API 风格 | REST + Webhook 回调 | gRPC | 对接飞书/钉钉/Jira 以 HTTP 为主，REST 足够 |
| 异步任务 | **Spring + Redis 队列 / 内存队列（MVP）** | RabbitMQ / Kafka | 一周内优先 Redis List + 重试；流量大再上 MQ |
| 数据库 | **MySQL 8** | PostgreSQL | 工单/错误事件结构化存储；公司普遍已有 MySQL |
| 缓存/去重 | **Redis 7** | Caffeine only | 指纹冷却、限流、幂等键、分布式锁 |
| ORM | **MyBatis-Plus** 或 **Spring Data JPA** | — | 二选一即可；建议 JPA 加速 CRUD，复杂 SQL 再补 |
| 日志 | Logback + JSON 布局 | — | 便于自监控与排查 |
| 可观测 | Micrometer + Actuator | — | 健康检查、指标暴露 |
| 错误捕获（业务侧） | **自研轻量 Java SDK**（HTTP 上报） | OpenTelemetry Java Agent 旁路 | 从零可控、体积小；OTel 可作为二期增强 |
| 错误捕获（日志侧） | Logback Appender 插件 | Filebeat → 本服务 | 本地/存量系统无改代码成本最低 |
| LLM | **OpenAI 兼容 HTTP API**（公司现有网关） | 直连厂商 SDK | 统一适配层，便于换模型；超时/重试可控 |
| 协作推送 | **飞书自定义机器人 Webhook**（优先） | 钉钉机器人 / 开放平台 | Webhook 最快打通；开放平台能力更强但审批慢 |
| 工单 | **Jira REST API v3** | — | 官方稳定；创建 Issue + 自定义字段足够 |
| 容器化 | Docker Compose | K8s | 一周内本机/单机部署即可 |
| 配置中心 | `application.yml` + 环境变量 | Nacos | MVP 够用；密钥不入库 |
| 文档 | Markdown + OpenAPI（springdoc） | — | 便于联调与验收 |

### 3.2 选型原则（贴合「一周加班」现实）

1. **优先可集成、少造轮子**：飞书/钉钉/Jira/LLM 全部走 HTTP，避免深度 SDK 绑定。  
2. **主路径先通**：先保证一条完整链路，再补本地 Appender、管理页、告警抑制。  
3. **可替换边界清晰**：`Notifier`、`LlmClient`、`IssueTracker`、`ErrorIngest` 全部接口化。  
4. **数据落库优先**：分析结论、工单号、推送结果必须可追溯，避免「只推了群消息却查不到历史」。

### 3.3 建议仓库模块划分

```text
aiea/
├── aiea-server          # Spring Boot 主服务：接入、分析、推送、建单
├── aiea-sdk             # 业务侧 Java SDK（异常上报）
├── aiea-logback-appender# Logback Appender（本地/无侵入）
├── aiea-common          # DTO、指纹算法、枚举
└── deploy/              # docker-compose、SQL 初始化脚本
```

## 4. 系统架构设计

### 4.1 逻辑架构

```text
┌─────────────────┐   ┌──────────────────────┐
│ 业务 Java 服务   │   │ 本地 IDE / 本地服务   │
│  + aiea-sdk     │   │  + Logback Appender  │
└────────┬────────┘   └──────────┬───────────┘
         │ HTTP 上报             │ HTTP 上报
         └───────────┬───────────┘
                     ▼
         ┌───────────────────────┐
         │     aiea-server       │
         │  Ingest → Dedup →     │
         │  Queue → LLM Analyze →│
         │  Notify → Create Jira │
         └───────┬───────────────┘
                 │
     ┌───────────┼───────────┬────────────┐
     ▼           ▼           ▼            ▼
  MySQL       Redis      LLM API    飞书/钉钉
                         Jira API
```

### 4.2 核心处理流水线

1. **Ingest**：校验 Token、限流、解析堆栈/上下文  
2. **Fingerprint**：归一化堆栈（去掉行号噪声可选）生成 `error_fingerprint`  
3. **Dedup / Suppress**：Redis 冷却窗口内同类错误合并计数，不重复分析或仅更新计数  
4. **Analyze**：拼装 Prompt，调用 LLM，结构化输出（JSON Schema）  
5. **Notify**：渲染 Markdown/卡片消息，推送群聊  
6. **Ticket**：创建 Jira Issue，回写 `jira_key`，并在群消息中附链接（可先建单再推送，或推送后补链）  
7. **Audit**：全链路状态机：`RECEIVED → ANALYZING → NOTIFIED → TICKETED → FAILED`

### 4.3 关键数据实体（简表）

| 实体 | 关键字段 |
|------|----------|
| `error_event` | id, fingerprint, env, service, message, stack, context_json, status, created_at |
| `analysis_result` | event_id, root_cause, suggestions, confidence, model, raw_response |
| `notify_record` | event_id, channel, payload, http_status, sent_at |
| `jira_ticket` | event_id, jira_key, project, url, created_at |
| `suppress_rule` | fingerprint, cooldown_sec, last_fired_at, hit_count |

## 6. 关键技术难点分析

以下难点容易在排期中被低估，建议提前预留应对时间。

### 6.1 错误指纹稳定性 vs 灵敏度

**挑战**：同一根因因行号变化、UUID、时间戳、容器 ID 导致指纹抖动，或过粗导致不同问题被合并。  

**解决思路**：
- 堆栈归一化：剔除消息中的动态段（数字、UUID、hex）；保留 Top N 帧（包名过滤 JDK/框架帧可选）
- 双层键：`fingerprint`（粗）+ `signature_hash`（细），抑制用粗键，详情用细键
- 提供手动「合并/拆分」运维接口（二期可做；MVP 用配置白名单）

### 6.2 LLM 输出不稳定与幻觉

**挑战**：模型偶发跑题、中英混杂、虚构不存在的类/方法、JSON 解析失败。  

**解决思路**：
- 强制 JSON Schema / 函数调用式输出；解析失败自动重试 1 次并降级为「原始摘要模板」
- Prompt 中明确「仅基于给定堆栈，未知则标注不确定」；给出置信度字段
- 对高危建议（删库、关鉴权等）做关键词拦截提示
- 缓存同指纹近期分析结果，避免重复消耗 Token

### 6.3 敏感信息泄露（PII / 密钥）

**挑战**：堆栈、HTTP Body、SQL、请求头可能含 Token、身份证、手机号；推送到群聊与 Jira 后扩散面大。  

**解决思路**：
- 上报前 SDK 侧与服务端双重脱敏（Authorization、password、cookie、手机号、邮箱正则）
- 群消息默认只发摘要 + 内部详情链接；完整堆栈仅存系统内
- 配置「详情可见范围」与审计日志；密钥仅环境变量注入

### 6.4 告警风暴与成本失控

**挑战**：线上突发大量同类/近似错误，导致 LLM 费用暴涨、群刷屏、Jira 工单爆炸。  

**解决思路**：
- Redis 冷却 + 计数合并（如 10 分钟合并）
- 全局限流（QPS）与每服务限流；LLM 日预算熔断
- 仅对「新指纹」或「严重级别」触发完整分析；重复错误只更新计数
- 死信队列与夜间汇总（MVP 可做简单「合并通知」）

### 6.5 本地环境与线上环境语义不一致

**挑战**：本地缺配置、测试数据导致的错误噪声大；若与线上同一通道，会污染工单。  

**解决思路**：
- 强制 `env` 字段（`local/dev/staging/prod`）；不同环境不同 Jira 项目或标签
- local 默认只推「个人/开发群」或仅入库不建单（可配置）
- SDK 读取 `spring.profiles.active` / 环境变量自动填充

### 6.6 飞书/钉钉与 Jira 的权限与字段差异

**挑战**：自定义字段必填、Issue Type 名称不一致、机器人频率限制、卡片 JSON 格式严格。  

**解决思路**：
- Day0 用最小字段集打通（Summary + Description + Labels）
- 适配器模式隔离差异；准备 Postman 集合先于写业务代码验证
- 对 API 限流做指数退避；失败落库可重放

### 6.7 同步链路耗时与用户体验

**挑战**：LLM 通常 2–10s，若在上报接口内同步调用会拖垮业务 SDK。  

**解决思路**：
- 上报接口只负责快速入库与入队（目标 P99 < 200ms）
- 分析/推送/建单全异步；提供查询 API 与群通知作为结果出口
- SDK 侧异步发送 + 本地失败缓冲（磁盘/内存队列，MVP 可简化为异步 HTTP）

### 6.8 堆栈上下文不足导致「分析没用」

**挑战**：仅有 Exception Message 时根因质量差；缺少请求参数、最近日志、版本、变更信息。  

**解决思路**：
- SDK 采集：服务名、版本、hostname、thread、MDC（traceId）、最近面包屑（面包屑限长）
- Prompt 引导「信息不足时列出需要补充的排查项」
- 二期接入 Git Blame / 最近发布版本（本周不做，但字段预留 `release_version`）

### 6.9 一周交付下的可测试性

**挑战**：外部依赖多（LLM/IM/Jira），CI 难以及时完备。  

**解决思路**：
- 所有外部依赖接口化 + WireMock/Mock 实现
- 提供 `demo` 模式：Mock LLM/Notifier/Jira，保证离线可演示
- 真实联调集中在 D4–D7，避免前期阻塞

## 7. 项目风险与应对策略

### 7.1 技术风险

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| LLM API 不稳定/延迟高 | 分析失败、体验差 | 中 | 超时降级模板；重试；结果缓存；异步化 |
| 飞书/钉钉鉴权或审核延迟 | 无法推送 | 中高 | Day0 申请；先 Webhook 后开放平台；备选邮件/企业微信 |
| Jira 必填字段未知 | 建单失败 | 中 | 提前用 API 探测 create meta；最小字段策略 |
| 指纹策略不当 | 漏报或刷屏 | 高 | 可配置冷却；先保守合并；提供强制重新分析接口 |
| 堆栈过大拖垮 DB/LLM | 性能与成本 | 中 | 截断（如 32KB）；只保留关键帧 |
| JDK/框架版本不兼容 | SDK 难接入 | 低 | SDK 面向 Java 11+；反射谨慎；提供 Appender 兜底 |

### 7.2 时间风险

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 范围膨胀（双 IM、漂亮前端、自动修复） | 主路径延期 | 高 | 严格 MVP；UI 可用 API/极简页替代 |
| 权限申请超过 2 天 | 关键联调阻塞 | 高 | 并行 Mock；用个人测试机器人先通 |
| 联调问题集中在最后两天 | 验收失败 | 中 | D2 起每日保留 1 个真实样例回归 |
| 个人单点（仅一人开发） | 生病/卡死即停 | 中 | 文档化决策；模块接口清晰；优先可演示竖切 |

**时间盒规则**：任一模块超过计划 0.5 天仍无可用增量，立即切换到「更简实现」（例如：先纯文本 Webhook，不做卡片；先同步建单字段写死）。

### 7.3 资源风险

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 无独立服务器 | 部署受限 | 中 | 本机 Docker Compose；借用开发机 |
| LLM Token 预算不足 | 无法分析 | 中 | 严格去重；本地用小模型；prod 才全量分析 |
| 无法拿到业务服务接入窗口 | 缺少真实数据 | 中 | 自建 demo-app + 录制堆栈回放 |
| Jira 项目权限不够 | 不能建单 | 中 | 申请专用 Project；或先建到沙箱项目 |

### 7.4 合规与组织风险

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 群聊泄露客户数据 | 合规事故 | 中 | 脱敏 + 摘要推送 + 内网详情 |
| 自动建单造成流程混乱 | 研发抵触 | 中 | 先灰度到一个团队；local 默认不建单 |
| 「AI 建议被当成真理」 | 错误修复方向 | 中 | 消息标明「AI 建议，需人工确认」+ 置信度 |

## 8. 验收标准总表

### 8.1 功能验收

- [ ] 业务 demo 或真实服务可通过 SDK 自动上报未捕获/捕获异常  
- [ ] 本地可通过 Logback Appender 上报 ERROR 日志  
- [ ] 服务端对错误去重/冷却生效，重复错误不重复建单刷屏  
- [ ] LLM 产出结构化根因分析并落库  
- [ ] 飞书或钉钉群聊收到包含摘要、建议、环境信息的消息  
- [ ] 自动创建 Jira 工单，消息中含工单链接  
- [ ] 全链路状态可查询；失败可重试  

### 8.2 非功能验收

- [ ] 上报接口快速返回（不含 LLM 同步等待）  
- [ ] 配置项（Webhook、Jira、LLM、冷却）可通过配置/Admin API 调整  
- [ ] 敏感信息脱敏规则生效（抽样检查）  
- [ ] Docker Compose 可一键启动依赖与服务  
- [ ] 提供 README：架构、配置、演示步骤、已知限制  

### 8.3 Demo 脚本（验收演示建议 10 分钟）

1. 启动 `docker compose` + server  
2. 运行 demo-app 触发异常  
3. 展示库中事件与分析结果  
4. 展示群消息与 Jira Issue  
5. 再次触发同类异常，展示合并/抑制效果

## 9. 后续演进建议

1. **OpenTelemetry 接入**：统一 Trace/Span 与错误关联，提升根因质量  
2. **相似错误检索（轻量 RAG）**：历史已修复工单作为上下文，减少幻觉

5. **自动修复实验**：对确定模式（空指针守卫、配置缺失）生成补丁建议（人工合并）  
6. **效果度量**：接入前后 MTTR、重复告警率、工单有效率看板
