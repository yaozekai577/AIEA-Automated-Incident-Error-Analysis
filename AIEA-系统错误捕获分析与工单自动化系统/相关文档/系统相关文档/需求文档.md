## 1 项目概述

### 1.1 项目背景与业务痛点

在企业级软件开发与运维场景中，异常处理链条长期存在以下结构性痛点：

**痛点一：异常发现滞后，依赖人工翻日志。**  
线上与本地开发环境的异常发现高度依赖人工巡检日志文件。开发者需要登录服务器、检索日志、定位堆栈，流程冗长。尤其在微服务架构下，一个业务请求横跨多个服务，异常散落在不同节点日志中，排查耗时巨大。从异常发生到开发人员感知，平均延迟可达数十分钟甚至数小时。

**痛点二：同类错误反复出现，缺乏沉淀与追踪。**  
同一根因的异常（如空指针、连接超时）在不同环境、不同时间反复触发时，每次都需从头排查。缺乏统一的错误指纹归集机制，历史排查经验无法复用。错误没有生命周期管理，"发现—处理—关闭"的闭环无从建立。

**痛点三：协作通知低效，群聊信息碎片化。**  
异常发现后，开发人员通常在飞书/钉钉群中手动粘贴堆栈截图，信息不完整、格式不统一。关键信息（环境、服务名、版本、traceId）缺失导致远程协作者难以快速理解上下文。重复错误频繁刷群，重要告警被淹没。

**痛点四：工单创建手工操作，流程割裂。**  
从发现异常到创建jira工单，需要手动复制堆栈、填写描述、选择项目、指派处理人。操作繁琐且容易遗漏关键信息。群聊讨论与工单系统脱节，处理进度无法追踪。

**痛点五：根因分析依赖经验，新人上手慢。**  
面对复杂堆栈，定位根因高度依赖资深开发者的经验。对于常见异常模式（空指针、连接池耗尽、OOM），缺少自动化辅助分析手段，每个开发者都在重复类似的推理过程。

### 1.2 项目目标、产品定位

**产品定位**：AIEA 是一款面向研发团队的 **AI 驱动的异常全生命周期管理平台**，将"异常捕获 → 智能去重 → AI 根因分析 → 群聊通知 → 工单闭环"全流程自动化，替代传统的人工翻日志—群里同步—手填工单的低效模式。

**核心目标**：

| 目标 | 度量标准 |
|------|---------|
| 异常自动捕获 | 业务系统通过 SDK 或 Logback Appender 接入，零侵入上报异常堆栈 |
| 同类错误智能归并 | 堆栈指纹归一化 + Redis 冷却窗口，冷却期内同类错误自动合并计数，不重复触发下游 |
| AI 根因分析 | 调用大模型（OpenAI 兼容协议）生成结构化根因报告与修复建议，含置信度评分 |
| 协作通知自动化 | 异常发生后自动推送飞书/钉钉群聊卡片消息，含摘要、AI 分析、工单链接 |
| 工单闭环管理 | 自动创建内置工单（AI 生成标题、智能定级），支持认领、解决、关闭、重开全流程 |
| 管理控制台 | React Web UI 可视化管理服务注册、通知路由、LLM 配置、告警规则、工单与统计 |

### 1.3 创新亮点

**亮点一：端到端 AI 根因分析流水线**  
区别于传统 APM 工具仅做错误采集与展示，AIEA 在异常入库后自动调用大模型进行根因分析，输出结构化 JSON 报告（根因描述、修复建议列表、置信度评分）。同指纹错误通过 Redis 缓存复用分析结果，避免重复消耗 Token。LLM 调用失败时自动降级为规则摘要模板，保证主链路不中断。

**亮点二：堆栈指纹归一化与智能告警抑制**  
通过堆栈归一化算法（去除行号噪声、UUID、hex 值、时间戳等动态段）生成 SHA-256 指纹，实现同根因错误的精准聚合。结合 Redis SET NX + INCR + TTL 实现冷却窗口机制，冷却期内同类错误自动合并计数并追加到关联工单时间线（复发记录），已解决工单在错误复发时自动重开。

**亮点三：轻量 SDK + Logback Appender 双模接入**  
自研无 Spring 依赖的轻量 Java SDK（仅依赖 Jackson，兼容 Java 8+），支持手动捕获（`Aiea.capture(e)`）和全局异常处理器自动上报两种模式。同时提供 Logback Appender 实现零侵入接入——存量系统仅需修改 `logback.xml` 配置即可自动上报 ERROR 级日志，无需改动任何业务代码。SDK 内置敏感信息脱敏（Bearer Token、password/api_key）和堆栈截断（32KB），保障数据安全。

**亮点四：AI 生成工单标题 + 智能定级 + 修复提示词一键复制**  
内置工单系统在创建时调用 LLM 生成简短中文工单标题（失败时降级为拼接标题），并根据异常消息关键词智能判定优先级（OOM/死锁→P0，空指针/SQL异常→P1，其他→P2）。工单详情页提供"修复提示词"一键复制功能，自动提取错误背景、代码位置、根因分析、修复建议并组装为结构化 Prompt，可直接粘贴给 AI 编程助手辅助修复。

## 2 用户与角色分析

### 2.1 研发工程师（业务系统接入方）

- **身份**：业务系统的开发者，负责将 AIEA SDK 集成到自己的服务中
- **使用目标**：以最小侵入成本接入 AIEA，使本服务异常能自动上报
- **主要操作**：
  - 在业务系统 `pom.xml` 中引入 `aiea-sdk` 依赖
  - 通过 `AieaConfig.builder()` 初始化 SDK（配置 serverUrl、apiToken、service、env）
  - 在业务代码中调用 `Aiea.capture(e)` 手动上报异常，或注册全局异常处理器实现自动上报
  - 或通过 Logback Appender 配置实现零侵入接入（仅修改 `logback.xml`）

### 2.2 运维管理员

- **身份**：负责 AIEA 平台配置与运维的管理人员
- **使用目标**：管理接入服务、配置通知路由、调整告警策略、监控系统运行状态
- **主要操作**：
  - 在「服务注册」页面注册新服务、生成/重置上报 Token、启用/禁用服务
  - 在「通知路由」页面为不同服务配置专属飞书/钉钉机器人 Webhook，测试连通性
  - 在「告警规则」页面查看冷却规则命中情况，调整单指纹冷却窗口
  - 在「系统配置」页面配置 LLM（Base URL / API Key / 模型 / 缓存 TTL），测试连通性
  - 在「仪表盘」查看全局统计概览与系统健康度

### 2.3 工单处理人（开发者/负责人）

- **身份**：认领和处理错误工单的研发人员
- **使用目标**：跟踪分配给自己的错误工单，推进解决并关闭
- **主要操作**：
  - 在「工单管理」页面按状态/处理人筛选工单列表
  - 认领工单（状态从 OPEN → IN_PROGRESS）
  - 查看工单详情：AI 根因分析、修复建议、操作时间线、修复提示词
  - 一键复制修复提示词，粘贴给 AI 编程助手辅助修复
  - 标记工单为已解决（填写解决方案）、关闭、忽略或重新打开
  - 变更工单优先级

### 2.4 技术负责人/项目经理

- **身份**：关注团队错误处理效率与质量的管理者
- **使用目标**：掌握全局错误趋势、AI 分析效果、工单处理进度
- **主要操作**：
  - 在「仪表盘」查看错误总数、唯一指纹数、通知成功率、AI 置信度分布、环境/服务分布
  - 查看近 7 天错误趋势、错误热力图（星期×小时）、智能洞察提示
  - 在「错误聚合」页面按指纹分组查看高频问题
  - 查看工单状态分布统计

## 3 总体业务描述

AIEA 的核心业务流程为一条端到端的自动化异常处理流水线，业务闭环如下：

**第一阶段：异常捕获与上报**  
业务系统通过 aiea-sdk（`Aiea.capture(e)` 或全局异常处理器）或 Logback Appender 捕获异常，异步 HTTP POST 上报到 AIEA Server 的 `/api/v1/errors` 接口，请求头携带服务专属 `X-AIEA-Token` 进行鉴权。SDK 自动采集 hostname、线程名、releaseVersion，并内置敏感信息脱敏。

**第二阶段：接入处理（同步快速返回）**  
AIEA Server 接收上报后，执行同步处理链：Token 鉴权 → 全局/每服务 QPS 限流（Redis 固定窗口）→ 服务端二次脱敏 → 堆栈归一化指纹计算（SHA-256）→ Redis 冷却窗口去重检查。若在冷却窗口内，标记为 `SUPPRESSED` 并合并计数，不触发下游流水线；否则落库 `error_event` 表（状态 `RECEIVED`），事务提交后触发异步流水线。上报接口同步返回，不等待 LLM 分析。

**第三阶段：异步流水线处理**  
异步流水线（`ErrorPipelineService`，`@Async`）按序执行：
1. **AI 根因分析**：检查同指纹 Redis 缓存，命中则复用；否则调用 LLM 生成结构化 JSON（根因/建议/置信度），解析失败自动重试并降级。分析结果落库 `analysis_result`。
2. **创建内置工单**：同指纹有未关闭工单则复用；否则调用 LLM 生成工单标题，根据异常关键词智能定级，创建内置工单（`internal_ticket`）。
3. **创建 Jira 工单**（可选）：若 Jira 已配置且环境允许，创建 Jira Issue 并记录关联。
4. **群聊通知**：按服务名+渠道查找通知路由规则，推送飞书/钉钉卡片消息（含摘要、AI 分析、工单链接），失败重试。

**第四阶段：人工协作与闭环**  
开发者在群聊中收到告警卡片，点击链接查看事件详情与 AI 分析。在管理控制台认领工单、查看修复提示词、推进解决并关闭。若冷却窗口内错误复发，系统自动在工单时间线追加复发记录；若工单已解决但错误仍在复发，自动重开工单。全链路状态可查询，失败可重试。

## 7 风险与局限
### 7.1 后续迭代方向

1. **分布式部署**：引入消息队列（Kafka/RabbitMQ）解耦异步流水线，支持多实例水平扩展
2. **用户认证与权限**：增加用户登录、角色权限（管理员/处理人/只读），支持多团队隔离
3. **分页与性能优化**：错误事件列表、统计概览改为数据库分页 + 聚合查询，支持大数据量
4. **RAG 增强**：接入向量数据库，将历史工单/修复记录作为 LLM 上下文，减少幻觉
5. **告警值班路由**：按服务 owner 自动路由通知到对应群/人，支持值班轮换
6. **效果度量**：接入前后 MTTR、重复告警率、工单有效率看板，量化工具价值
